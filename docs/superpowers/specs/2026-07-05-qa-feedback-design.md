# QA 피드백 반영 설계

## 목표

첫 사용자 QA에서 발견된 입력 마찰과 매칭 이후의 단절을 제거한다. 교환 글은 선택 중심으로 빠르게 등록하고, 새 매칭을 화면 어디서든 인지하며, 참여자 전원이 수락하면 실제 거래 진행 상태로 전환한다.

## 교환 글 UX

- 교환 글 카드는 제목뿐 아니라 카드 전체가 상세 링크다. 키보드 포커스와 hover 상태를 제공한다.
- 거래 지역은 자유 입력 대신 대한민국 17개 광역시·도 선택 상자를 사용한다.
- `희망 이름`은 `희망 물품·서비스`로 표시한다.
- 세부 카테고리는 선택 사항이며 빈 문자열을 `null`로 정규화한다.
- 가치 방식은 `DIRECT`(직접 입력), `NEGOTIABLE`(협의 가능), `OFFER_REQUESTED`(상대 제안 받기)다. `DIRECT`일 때만 제공 가치 또는 희망 가치 범위를 필수 입력으로 검증한다.
- 제출 시 누락된 필수 입력에 `aria-invalid`와 빨간 테두리·필드 메시지를 표시하고 첫 오류 필드로 포커스를 이동한다.

## 데이터와 매칭

- 제공·희망 항목에 `value_policy`를 추가하고 금액과 세부 카테고리 컬럼을 nullable로 변경한다.
- 기존 데이터는 `DIRECT`로 이관한다.
- 양쪽 모두 금액을 제공할 때만 기존 가치 점수를 계산한다. 어느 한쪽이라도 비금액 정책이면 가치 점수는 0점이고 카테고리·이름·태그·지역·신뢰도 규칙은 그대로 적용한다.

## 실시간 인지와 알림

- 로그인 상태에서 알림 API를 15초마다 조회한다. 초기 조회 이후 새 unread 알림이 나타나면 상단 toast를 노출한다.
- 내비게이션의 `알림`에는 unread 개수 배지를, 매칭 알림이 unread이면 `매칭`에도 빨간 점을 표시한다.
- 알림은 `referenceId`로 매칭 후보를 참조한다. 매칭 알림 카드를 누르면 읽음 처리 후 `/matches/{id}`로 이동한다.
- 탭 비활성화 후 복귀하면 즉시 다시 조회한다. WebSocket/SSE는 MVP 이후로 둔다.

## 거래 수락 흐름

- 매칭 상세에서 현재 사용자는 `참여 수락` 또는 `거절`할 수 있다.
- 수락은 자기 `MatchParticipant.acceptStatus`만 변경한다. 전원 수락 시 `MatchCandidate.status=ACCEPTED`, 관련 글은 `IN_EXCHANGE`로 전환한다.
- 한 명이라도 거절하면 후보는 `REJECTED`가 되며 이후 상태 변경은 막는다.
- 상태 변경 결과는 모든 참여자에게 알림으로 전달한다. 실제 채팅·결제·완료 처리는 이번 범위에 포함하지 않는다.

## 오류와 테스트

- 본인이 참여하지 않은 매칭 접근은 403, 이미 종료된 후보 변경은 409로 응답한다.
- 백엔드는 nullable 가치 점수, 선택 세부 카테고리, 수락/거절/전원 수락, 알림 reference를 통합 테스트한다.
- 프론트는 카드 전체 링크, 조건부 가치 입력, 필드 강조, 배지·toast, 알림 이동, 수락 버튼을 Testing Library로 검증한다.
