# ValueSwap MVP 설계 명세

## 1. 목표와 범위

ValueSwap은 두 사용자 사이의 상호 교환과 3~4명 사이의 방향성 교환 순환을 찾는 규칙 기반 물물교환 플랫폼이다. MVP는 외부 AI API, 결제, 지도, Kafka, Redis, 실시간 소켓을 사용하지 않고 실제로 실행되는 Spring Boot API, React 웹 클라이언트, MySQL 스키마, 초기 데이터와 자동화 테스트를 제공한다.

제품은 하나의 일관된 애플리케이션 안에서 다음 두 구현 단계로 완성한다.

1. 핵심 교환 단계: 인증, 교환 글 CRUD, 항목 점수 계산, 2~4자 순환 탐색, 매칭 후보 저장, 알림, 연동된 React UI
2. 거래 단계: 제안방, 메시지, 만장일치 수락 또는 거절, 완료 확인, 교환권, 후기, 신뢰도, 관리자 기능

## 2. 아키텍처

저장소는 `backend`, `frontend` 애플리케이션과 루트 운영 문서 및 Docker Compose 설정으로 구성된 모노레포로 만든다.

백엔드는 모듈형 모놀리스로 구현한다. 각 도메인 모듈은 API, 애플리케이션 서비스, 영속성, DTO 책임을 함께 가지며 공통 보안과 예외 처리는 기반 모듈에 둔다. Controller는 JPA Entity를 직접 반환하지 않으며 상태 변경 유스케이스는 트랜잭션으로 처리한다.

프론트엔드는 Vite 기반 React SPA로 구현한다. React Router로 화면을 전환하고 Axios로 API를 호출하며, 인증 Context로 최소한의 세션 상태를 관리한다. 서버 데이터의 기준은 항상 백엔드이다.

## 3. 백엔드 모듈

- `auth`: 회원가입, 로그인, 현재 사용자 조회, BCrypt 비밀번호 암호화, JWT 생성 및 검증
- `user`: 사용자 프로필, 역할, 신뢰도 계산 결과, 관리자 사용자 조회
- `post`: 교환 글, 제공 항목, 희망 항목, 소유권 검사, 상태 전이 규칙
- `matching`: 항목 점수 계산, 방향 간선 생성, 순환 탐색, 후보 저장, 수동 및 자동 실행
- `notification`: 사용자별 알림과 읽음 상태
- `room`: 제안 생성, 참여자, 메시지, 수락, 거절, 완료 확인
- `voucher`: UUID 교환권 발급, 소유자 조회, 발급자 전용 사용 처리, 만료
- `review`: 완료된 거래의 후기 권한, 중복 방지, 평점 집계
- `report`: 로그인 사용자의 게시글 신고, 신고 사유, 관리자 처리 상태
- `admin`: 사용자·게시글·신고 조회와 게시글 숨김
- `common`: 보안, 예외, 시간 공급자, 검증, 공통 응답 규칙

## 4. 도메인 모델 결정

요구사항의 핵심 Entity를 유지하고 유스케이스를 명확하게 만들기 위해 다음 필드와 모델을 추가한다.

- `MatchParticipant.completedAt`: 참여자별 거래 완료 확인 시각
- `ExchangeRoomMessage`: 데이터베이스에 저장하고 폴링으로 조회하는 메시지. MVP에는 WebSocket을 사용하지 않는다.
- `Voucher.provideItem`: 교환권이 나타내는 서비스형 제공 항목
- `Review`: `(reviewer_id, target_user_id, exchange_room_id)` 복합 유일 제약
- `Report`: 신고자, 신고 게시글, 사유, 상태, 처리 관리자, 처리 시각. 한 사용자는 같은 글을 한 번만 신고할 수 있다.
- `MatchCandidate.cycleKey`: 게시글 조합을 나타내는 유일 정규 키
- `ExchangeRoom.matchCandidate`: 매칭 후보별 중복 방 생성을 막는 일대일 유일 관계
- 태그는 정규화된 별도 컬렉션 테이블에 저장한다.

금액은 원화 정수인 `Long`으로 저장한다. 평점은 1~5 정수이다. `trustScore`는 0~100 범위의 소수이며 신규 사용자의 초기값은 50이다. 후기 등록 후 평균 평점을 0~100 범위로 선형 변환하여 갱신한다.

교환 글 삭제는 실제 삭제 대신 `CANCELED` 상태로 전환한다. 작성자만 글을 수정하거나 취소할 수 있고 `ACTIVE` 상태에서만 가능하다. 관리자가 글을 숨기면 `HIDDEN`으로 전환한다.

## 5. 항목 매칭

`ItemMatchScorer`는 하나의 `WantItem`과 하나의 `ProvideItem`, 두 게시글의 지역, 제공자의 신뢰도를 비교한다. 문자열은 유니코드 정규화, 소문자 변환, 연속 공백 축약, 구두점 분리 과정을 거친다.

점수는 요구사항의 가산 규칙을 따른다.

- category 일치: 25점
- subCategory 일치: 25점
- 정규화한 이름 완전 일치: 30점
- 제공 이름이 희망 이름을 포함: 20점
- 희망 이름이 제공 이름을 포함: 20점
- 정규화한 이름 토큰이 하나 이상 일치: 10점
- 태그 일치: 개당 5점, 최대 20점
- 예상 가치가 희망 범위 안에 있음: 20점
- 희망 범위의 가까운 경계에서 20% 이내로 벗어남: 5점
- 정규화한 지역 일치: 10점
- 제공자 신뢰도 기여: `trustScore / 10`, 0~10점으로 제한

총점이 60점 이상이어야 하며 category가 같고 subCategory 일치, 이름 일치·포함·토큰 중복, 태그 중복 중 하나 이상을 만족해야 간선 후보가 된다. 이 보조 조건으로 category만 같은 광범위한 오매칭을 막는다.

순서가 있는 두 게시글 조합마다 모든 희망·제공 항목 쌍을 비교하고, 조건을 통과한 항목 중 점수가 가장 높은 한 쌍만 방향 간선으로 선택한다. 같은 게시글 및 같은 사용자가 소유한 서로 다른 게시글 사이에는 간선을 만들지 않는다.

## 6. 교환 순환 탐색

각 `ACTIVE` 교환 글을 그래프 노드로 본다. `A -> B` 간선은 A의 희망 항목을 B의 제공 항목이 만족한다는 의미이다.

순환 탐색기는 깊이를 제한한 DFS로 길이 2, 3, 4의 단순 순환을 찾는다. 한 경로에서 게시글이나 사용자를 반복할 수 없고 마지막 간선은 시작 노드로 돌아와야 한다. `ACTIVE`가 아닌 게시글은 모두 제외한다.

요구된 중복 기준에 따라 순환에 포함된 게시글 ID를 정렬해 `-`로 연결한다. 순환 길이에 따른 유형도 키에 포함한다. 예를 들어 `THREE_PARTY:1-4-9` 형식이다. 따라서 시작점만 다른 순환과 동일한 게시글 조합의 다른 탐색 결과는 후보 하나로 처리한다.

저장되는 매칭 후보는 다음 정보를 포함한다.

- 순환 길이에서 결정한 match type
- 포함된 간선 점수의 평균
- 탐색된 교환 흐름 순서의 참여자
- 선택한 희망·제공 항목을 포함한 각 간선
- `FOUND` 상태 및 참여자의 `PENDING` 수락 상태
- 참여 사용자별 `MATCH_FOUND` 알림 한 건

`cycleKey`에 유일 제약을 두고 기존 후보를 건너뛰므로 수동 또는 자동 탐색을 반복해도 같은 후보가 중복 생성되지 않는다.

매칭 후보의 평균 간선 점수를 해당 후보의 가중치 점수로 사용한다. 사용자별 매칭 목록은 이 점수의 내림차순으로 정렬하고, 점수가 같으면 생성 시각이 최신인 후보를 먼저 표시한다. 따라서 사용자는 교환 가능성이 높은 후보부터 확인할 수 있다.

간선 점수가 기준점인 60점 이상이고 완전한 2~4자 순환을 이룬 후보가 새로 저장되면 관련 사용자 모두에게 알림을 생성한다. 반복 탐색에서 이미 존재하는 `cycleKey`에는 알림을 다시 만들지 않아 중복 알림을 방지한다. 알림 발생 기준점은 운영 중 조정할 수 있도록 환경 설정값으로 분리하되 기본값은 60으로 둔다.

## 7. 제안과 거래 상태

참여자는 누구나 `FOUND` 후보를 제안할 수 있다. 제안하면 `OPEN` 방을 하나 만들고 후보를 `PROPOSED`로 변경하며 모든 참여자에게 알린다.

수락은 하나의 트랜잭션에서 처리한다. 데드락 가능성을 낮추기 위해 관련 게시글을 ID 오름차순으로 비관적 잠금한다. 어느 글이라도 더 이상 거래할 수 없으면 409 충돌로 실패하고 아무 상태도 변경하지 않는다. 모든 참여자가 수락하면 후보와 방은 `ACCEPTED`, 게시글은 `IN_EXCHANGE`가 되며 필요한 교환권을 발급한다.

한 명이 거절하면 후보와 방은 즉시 `REJECTED`가 된다. 확정된 다른 거래가 없는 관련 게시글은 `ACTIVE`로 복구하고 이후 참여자 결정은 받지 않는다.

수락 후 각 참여자는 완료를 한 번만 확인할 수 있다. 모두 확인하면 방, 후보, 게시글을 `COMPLETED`로 바꾸고 알림을 생성한다. 동일한 완료 요청은 결과가 달라지지 않도록 멱등 처리한다.

## 8. QR 교환권

제공 항목 category가 `FOOD`, `COUPON`, `SERVICE`, `TALENT`, `DESIGN`, `BEAUTY`, `LESSON` 중 하나이면 교환권을 발급한다. 방향 간선 `A -> B`에서 제공자인 B가 issuer이고 제공을 받는 A가 owner이다. 코드는 임의 UUID이며 발급 30일 후 만료된다.

owner는 교환권과 QR 표시를 조회할 수 있다. issuer 또는 관리자만 사용 처리할 수 있다. 사용 처리는 교환권을 잠근 뒤 `ISSUED` 상태와 만료 여부를 검사하고 한 번만 `USED`로 전환한다. 만료된 교환권은 조회 시점과 주기 작업에서 `EXPIRED`로 전환한다.

## 9. 후기와 신뢰도

후기는 방이 완료된 뒤 같은 방의 서로 다른 참여자 사이에서만 작성할 수 있다. 동일한 작성자·대상·방 조합에는 한 번만 작성할 수 있다. 후기 저장 후 대상 사용자의 평균 평점을 다시 계산하고 0~100 신뢰도로 변환한다. 후기 응답에는 작성자 표시 정보, 평점, 내용, 작성 시각만 포함하며 비공개 사용자 정보는 노출하지 않는다.

## 10. API와 오류 계약

요구사항에 명시된 모든 API를 구현한다. 빠져 있던 신고 내역 기능을 위해 `POST /api/posts/{postId}/reports`, `GET /api/admin/reports`를 추가한다. 목록 API는 제한된 페이지 크기의 페이지네이션을 지원한다. 게시글 목록은 상태, 지역, category, 검색어로 선택 필터링할 수 있다.

정상 응답은 목적별 DTO를 반환한다. 오류는 발생 시각, HTTP 상태, 애플리케이션 오류 코드, 메시지, 경로, 선택적인 필드 검증 오류를 가진 공통 JSON 형식을 사용한다. `GlobalExceptionHandler`는 검증 오류를 400, 미인증을 401, 권한 부족을 403, 리소스 없음은 404, 상태·중복 충돌은 409, 예상하지 못한 오류는 500으로 변환한다.

JWT access token에는 사용자 ID와 역할을 포함하며 만료 시간은 설정으로 관리한다. 서명 비밀값과 데이터베이스 인증 정보는 환경 변수로 주입한다. `/api/auth/signup`, `/api/auth/login`과 읽기 전용 게시글 조회는 공개하고 나머지는 인증을 요구한다. 매칭 수동 실행과 관리자 API는 `ADMIN`만 호출할 수 있다.

## 11. 프론트엔드 경험

시각 방향은 관리 도구처럼 보이는 화면이 아니라 깔끔하고 친근한 교환 장터로 잡는다. 사용자가 무엇을 제공하고 무엇을 받으며 가치가 순환 안에서 어떻게 이동하는지 쉽게 이해하는 것이 핵심이다.

로그인·회원가입, 대시보드, 게시글 목록·상세·작성·수정, 내 매칭, 매칭 상세, 제안방, 알림, 교환권, 후기, 관리자 사용자·게시글·신고 화면을 제공한다. 재사용 가능한 교환 흐름 컴포넌트는 2~4명의 참여자 카드를 방향 화살표로 연결하고 간선마다 제공 항목과 점수를 표시한다.

모바일 너비까지 반응형으로 동작한다. 게시글 폼은 여러 제공·희망 항목 추가와 삭제, 태그 칩, 필드 검증, 로딩·빈 결과·오류 상태를 지원한다. JWT는 MVP 범위에서 브라우저 local storage에 보관하고 Axios interceptor로 전송한다. 401 응답을 받으면 로컬 세션을 지우고 로그인 화면으로 이동한다.

## 12. 초기 데이터

초기 데이터는 로컬 개발 profile에서만 활성화하고 여러 번 실행해도 중복 생성되지 않게 한다. 관리자 계정, 식당·농가·디자이너의 3자 교환 사례, 햄버거·세제의 부분 이름 1:1 사례를 생성한다. 계정과 비밀번호는 README에 기록한다.

초기 데이터로 수동 매칭을 실행하면 `THREE_PARTY` 후보가 최소 하나, `ONE_TO_ONE` 후보가 최소 하나 생성되어야 한다.

## 13. 테스트와 검증

백엔드 테스트는 JUnit 5, AssertJ, 필요한 경우 Mockito, MySQL 호환 모드의 H2를 사용하는 Spring Boot 통합 테스트로 구성한다. 다음 동작은 반드시 검증한다.

- 모든 항목 점수 규칙과 category 단독 매칭 방지 조건
- 부분 이름 및 태그 중복 예시
- 순환 시작점 중복 제거와 동일 사용자 반복 제외
- 2자, 3자, 4자 순환 탐색
- JWT 인증, 소유권, 역할 권한
- 만장일치 수락, 거절, 비관적 잠금 충돌
- 교환권 owner·issuer·상태 규칙
- 거래 완료, 후기 권한, 신뢰도 재계산
- 초기 데이터에서 실제 매칭 후보 저장

프론트엔드는 주요 컴포넌트와 보호된 경로를 현실적인 범위에서 테스트한다. 최종 검증에서는 백엔드 전체 테스트, 프론트엔드 테스트, 프론트엔드 production build를 실행하고 Docker를 사용할 수 있으면 Docker Compose 기동도 확인한다.

## 14. 운영 산출물

- 사전 요구사항, 환경 변수, 로컬·Docker 실행법, 초기 계정, 주요 작업을 설명하는 루트 README
- 도메인별 요청·응답 예시를 포함한 API 문서
- JPA migration으로 표현하고 관계를 문서화한 MySQL 스키마
- 실제 비밀값이 없는 `.env.example`
- MySQL과 선택적인 애플리케이션 서비스를 실행하는 Docker Compose
- 5분 간격 매칭 및 교환권 만료 스케줄러 설정. 테스트에서는 비활성화하거나 주기를 조정할 수 있어야 한다.
- 외부 AI 서비스나 숨겨진 네트워크 의존성 없음

### 환경변수와 비밀정보 보호

- 실제 환경 파일인 `.env`, `.env.*`, `application-local.yml`, `application-secret.yml`과 개인 키 파일(`*.pem`, `*.key`, `*.p12`)은 `.gitignore`에 등록한다. 단, `.env.example`은 추적한다.
- 저장소에 포함되는 `application.yml`에는 `${DB_PASSWORD}`, `${JWT_SECRET}`처럼 환경변수 참조와 비밀이 아닌 기본값만 둔다.
- `.env.example`에는 변수 이름과 안전한 예시값만 기록하며 실제 데이터베이스 비밀번호, JWT 서명 키, 운영 도메인 인증 정보는 넣지 않는다.
- Docker Compose도 실제 값을 파일에 직접 쓰지 않고 환경변수 또는 로컬 `.env`에서 주입받는다.
- 커밋 전 추적 파일에서 비밀번호, 토큰, 개인 키 패턴을 검사한다. 비밀값이 발견되면 커밋과 푸시를 중단한다.

## 15. 완료 조건

새로 받은 저장소에서 MySQL 기반 애플리케이션을 실행하고 다음 시나리오를 끝까지 수행할 수 있으면 MVP가 완료된 것으로 본다.

1. 초기 사용자 또는 새 사용자로 로그인한다.
2. 교환 글을 등록한다.
3. 수동 탐색으로 요구된 1:1 및 3자 초기 매칭을 찾는다.
4. React 화면에서 방향성 교환 흐름을 확인한다.
5. 매칭을 제안하고 게시글 중복 거래 없이 전원이 수락한다.
6. 필요한 교환권을 발급하고 권한 있는 발급자가 사용 처리한다.
7. 모든 참여자가 거래 완료를 확인한다.
8. 허용된 상대에게 후기를 작성한다.
9. 관리자가 보호된 API와 화면에서 사용자, 게시글, 신고를 관리한다.
