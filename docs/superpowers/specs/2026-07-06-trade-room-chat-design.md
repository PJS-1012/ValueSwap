# 거래방과 실시간 텍스트 채팅 설계

## 목표

매칭 참여자 전원이 수락하면 참여자 전용 거래방을 하나 생성한다. 사용자는 상단 `대화` 메뉴에서 진행 중이거나 완료된 모든 거래방을 확인하고 실시간 텍스트 대화를 나누며, 모든 참여자가 거래 완료를 확인하면 거래 흐름을 종료할 수 있다.

## 범위

이번 단계에는 텍스트 메시지, 과거 메시지 조회, 읽음 상태, 안 읽은 메시지 배지, 거래 완료 확인을 포함한다. 이미지·파일 첨부, 메시지 수정·삭제, 거래 취소·분쟁, 후기·신뢰도 재계산은 제외한다.

## 데이터 모델

- `TradeRoom`: 매칭 후보와 일대일 관계이며 `IN_EXCHANGE`, `COMPLETED` 상태와 생성·완료 시각을 가진다.
- `TradeRoomMember`: 거래방과 사용자 조합을 유일하게 저장하고 `lastReadMessageId`, `completedAt`을 가진다.
- `ChatMessage`: 거래방, 발신자, 클라이언트 임시 ID, 1~1000자의 본문과 생성 시각을 저장한다.

DB 마이그레이션은 거래방, 구성원, 메시지 테이블과 목록·메시지 조회에 필요한 인덱스를 추가한다. `match_candidate_id`에 유일 제약을 둬 동시 요청에서도 거래방이 중복 생성되지 않게 한다.

## 거래방 생명주기

마지막 참여자가 매칭을 수락하는 트랜잭션에서 후보와 게시글을 거래 진행 상태로 바꾸고 거래방과 모든 구성원을 생성한다. 이미 방이 존재하면 기존 방을 반환해 같은 요청의 결과가 달라지지 않게 한다.

각 구성원은 거래 완료를 한 번만 확인할 수 있다. 모든 구성원의 `completedAt`이 채워지면 거래방과 매칭 후보를 `COMPLETED`로, 관련 게시글을 `COMPLETED`로 전환하고 참여자 전원에게 완료 알림을 생성한다. 완료된 방은 목록과 과거 메시지를 계속 제공하지만 새 메시지 전송은 409로 거부한다.

## API와 실시간 통신

REST API는 내 거래방 목록, 거래방 상세, 커서 기반 과거 메시지 조회, 읽음 처리, 거래 완료 처리를 제공한다. 목록은 최근 메시지 시각 내림차순이며 최근 메시지가 없는 방은 생성 시각을 사용한다.

Spring WebSocket과 STOMP를 사용한다. 클라이언트는 `/ws`로 연결하고 STOMP `CONNECT` 헤더에 기존 JWT를 전달한다. 서버의 인바운드 채널 인터셉터는 연결·구독·발행마다 JWT와 거래방 구성원 권한을 검사한다. 클라이언트는 `/app/trade-rooms/{roomId}/messages`로 전송하고 `/topic/trade-rooms/{roomId}`를 구독한다. 서버는 메시지를 DB에 저장한 뒤 저장된 메시지 응답만 브로드캐스트한다.

연결이 끊기면 클라이언트는 지수형 지연으로 재연결한다. 재연결 후 마지막으로 받은 메시지 ID 이후의 메시지를 REST로 조회해 누락을 복구한다. 클라이언트가 생성한 임시 ID를 메시지 요청에 포함하고 방·발신자·임시 ID에 유일 제약을 둬 재전송 중복을 방지한다.

## 화면

상단 메뉴에 `대화`를 추가하고 전체 안 읽은 메시지 수를 빨간 배지로 표시한다. 전체 및 방별 배지는 1~99를 그대로 표시하고 100개 이상은 `99+`로 표시한다. 대화 목록 카드에는 참여자, 관련 게시글, 최근 메시지, 시각, 거래 상태, 방별 안 읽은 수를 표시한다. 카드를 선택하면 `/trades/{roomId}`로 이동한다.

거래방 화면에는 참여자와 교환 흐름, 메시지 내역, 입력창, 참여자별 완료 상태와 `거래 완료` 버튼을 표시한다. 각 메시지에는 한국 시간 기준 전송 시각을 표시한다. 오늘 보낸 메시지는 `오후 2:35`, 같은 해의 이전 날짜는 `7월 6일 오후 2:35`, 이전 연도는 `2025년 12월 31일 오후 11:20` 형식을 사용한다. 새 메시지를 받으면 하단에 가까운 경우 자동 스크롤하고, 이전 메시지를 읽는 중이면 새 메시지 안내만 표시한다. 완료된 방은 입력창 대신 읽기 전용 안내를 표시한다.

## 권한과 오류 처리

- 로그인하지 않은 REST·WebSocket 요청은 401이다.
- 거래방 비참여자의 조회·구독·전송·완료 요청은 403이다.
- 빈 메시지, 1000자 초과 메시지는 400이다.
- 완료된 방의 메시지 전송은 409이다.
- 읽음·완료 요청은 반복 호출해도 같은 결과를 반환한다.
- WebSocket 연결 실패는 화면 전체를 막지 않고 재연결 상태와 REST 복구를 안내한다.

## 테스트

- 마지막 수락 시 방과 구성원이 한 번만 생성되는 통합 테스트
- 비참여자 접근, 완료 방 전송, 메시지 길이, 중복 전송 테스트
- 메시지 저장 후 STOMP 구독자에게 전달되는 WebSocket 통합 테스트
- 읽지 않은 수와 읽음 처리, 전원 완료 상태 전환 테스트
- 대화 메뉴의 99·100개 배지 경계, 메시지 날짜별 시간 포맷, 목록 정렬, 메시지 전송·수신·재연결 복구, 완료 방 읽기 전용 프론트 테스트
- 백엔드 전체 테스트, 프론트 전체 테스트와 프로덕션 빌드

## 사용자 QA

서로 다른 브라우저나 시크릿 창에서 참여자 계정으로 로그인한다. 전원이 수락한 뒤 각 계정에 같은 거래방이 생기는지, 메시지가 실시간으로 전달되고 새로고침 후에도 남는지, 안 읽은 배지가 사라지는지 확인한다. 마지막으로 모든 계정에서 완료를 누른 뒤 방과 게시글이 완료 상태가 되고 메시지 전송이 막히는지 확인한다.
