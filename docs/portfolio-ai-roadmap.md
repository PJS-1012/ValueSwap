# ValueSwap 포트폴리오/AI 확장 로드맵

이 문서는 현재 MVP를 포트폴리오에서 설명하기 좋게 정리하고, 다음 단계로 AI 기능을 자연스럽게 붙이기 위한 작업 기준입니다.

## 현재 MVP에서 강조할 포인트

ValueSwap은 단순 게시판이 아니라, 서로의 필요와 제공 가치를 연결해 2~4명 교환 경로를 찾는 서비스입니다.

- Spring Boot + React 기반 풀스택 구현
- JWT 인증, 회원가입/로그인, 교환 글 CRUD
- 100점 만점 적합도 기반 매칭
- 다자간 순환 교환 후보 탐색
- 매칭 알림, 읽음 처리, 미확인 배지
- 거래 전원 수락 후 실시간 거래방 생성
- WebSocket/STOMP 기반 텍스트 채팅
- 전체 안 읽은 메시지 수 99+ 표시
- 거래 완료 상태 관리
- Docker Compose 기반 로컬 MySQL 실행
- `.env` 기반 로컬 환경변수 분리

## 포트폴리오에서 말하면 좋은 개발 경험

### 1. AI 도구를 쓴 방식

“AI가 만들어줬다”가 아니라, “AI를 코드 작성 보조/검증 파트너로 사용했다”로 설명하는 것이 좋습니다.

강조할 수 있는 내용:

- 요구사항 우선순위는 직접 정했다.
- Codex를 통해 구현 속도를 높였지만, 최종 판단은 직접 했다.
- 버그가 생겼을 때 원인, 수정 위치, 재발 방지 테스트를 확인했다.
- 기능 추가마다 테스트/빌드로 검증했다.
- 실제 비밀값은 `.env`로 분리하고 Git에 올리지 않도록 관리했다.

### 2. 트러블슈팅 사례

포트폴리오에는 “기능 목록”보다 “문제를 어떻게 해결했는지”가 더 강합니다.

대표 사례:

- WebSocket 메시지 전송 실패
  - 원인: STOMP 인터셉터에서 인증 정보가 원본 메시지 헤더에 유지되지 않음
  - 해결: `MessageHeaderAccessor.getAccessor(...)`로 실제 헤더 접근 후 사용자 인증 유지
  - 재발 방지: 인터셉터 회귀 테스트 추가
- Docker MySQL 로컬 실행
  - 원인: Docker Desktop 데몬이 실행되지 않으면 compose 명령이 MySQL 컨테이너를 띄울 수 없음
  - 해결: Docker Desktop 실행 후 `docker compose --env-file .env up -d mysql`
- 환경변수 혼동
  - 원인: OS 전역 환경변수와 프로젝트 `.env`의 우선순위/범위 차이
  - 해결: 프로젝트 로컬 `.env`를 기준으로 실행하도록 정리

## 다음 AI 기능 추천

현재 구조에서는 RAG보다 “AI 매칭 보조 Agent”가 더 자연스럽습니다.

### AI 매칭 보조 Agent

사용자가 교환 글을 등록하거나 매칭 후보를 확인할 때, AI가 다음을 설명합니다.

- 이 매칭이 왜 적합한지
- 어떤 조건이 잘 맞는지
- 어떤 조건 때문에 점수가 낮아졌는지
- 다자간 거래에서 누가 무엇을 주고받는지
- 사용자가 수정하면 매칭 가능성이 올라가는 항목

예시:

> 적합도 86점  
> 식당은 농산물을 원하고, 농가는 디자인 작업을 원하며, 디자이너는 식사권을 원합니다. 세 참여자의 필요가 순환 구조를 이루므로 다자간 교환 가능성이 높습니다.

### RAG가 어울리는 확장 영역

RAG는 지금 당장 핵심 기능에 필수는 아니지만, 아래 기능에는 잘 맞습니다.

- 거래 안전 가이드 기반 위험 문구 감지
- 서비스 이용 정책/FAQ 챗봇
- 금지 품목/주의 품목 안내
- 과거 거래 사례 기반 유사 거래 참고

## AI 기능 1차 구현 범위

처음부터 복잡한 Agent 프레임워크를 붙이지 말고, Spring Boot 서비스 하나로 작게 시작하는 것을 추천합니다.

### 백엔드

- `AiMatchExplanationService`
  - 매칭 후보 데이터 입력
  - LLM에 전달할 프롬프트 생성
  - 적합도 설명 문장 반환
- `POST /api/matches/{matchId}/explanation`
  - 특정 매칭 후보의 AI 설명 생성
- `GET /api/matches/{matchId}/explanation`
  - 이미 생성된 설명 조회

### 프론트엔드

- 매칭 상세 화면에 “AI 분석 보기” 버튼 추가
- 적합도 점수 옆에 설명 카드 표시
- 100점 만점 기준 안내와 함께 표시

### 데이터

처음에는 설명을 DB에 저장하지 않고 즉시 생성해도 됩니다.  
다만 비용과 응답 속도를 고려하면, 이후에는 생성된 설명을 저장하고 재사용하는 구조가 좋습니다.

## 구현 우선순위

1. 현재 MVP QA 체크리스트 수행
2. README/포트폴리오 문서 정리
3. AI 매칭 설명 기능 설계 확정
4. OpenAI API 키를 `.env`에만 추가
5. 백엔드 AI 설명 서비스 구현
6. 프론트 매칭 상세 화면에 설명 카드 추가
7. 비용/실패/타임아웃 처리

## 주의사항

- OpenAI API 키 같은 실제 비밀값은 절대 Git에 올리지 않습니다.
- `.env.example`에는 변수 이름만 추가하고 실제 값은 넣지 않습니다.
- AI 응답은 참고 정보로 표시하고, 최종 거래 판단은 사용자에게 맡깁니다.
- AI 기능 실패 시에도 기존 매칭 기능은 정상 동작해야 합니다.
